# Security

TripCash holds people's money records and shares them between phones.
Security reports are welcome and will be taken seriously.

## Reporting a vulnerability

Please report privately first, not in a public issue.

Use GitHub's **Report a vulnerability** button under the Security tab of
this repository, which opens a private advisory visible only to the
maintainers.

Please include what you found, how to reproduce it, and what an attacker
could actually do with it. A proof of concept helps enormously.

You will get an acknowledgement within a few days. Please give a
reasonable window to ship a fix before disclosing publicly.

## Scope

In scope:

- The security rules in `firestore.rules` and `storage.rules` — anything
  that lets one account read or write another's trip.
- The Cloud Functions in `functions/` — anything that leaks data across
  accounts, or that an unauthenticated caller can abuse.
- The client in `js/` — anything that discloses another user's data, or
  that lets a shared trip's member escalate beyond what the rules intend.
- The invitation flow — anything that lets someone join a trip they were
  never invited to, or enumerate who uses the app.

Out of scope:

- Reports generated by scanners with no demonstrated impact.
- Missing headers or cookie flags with no exploit path. The app sets no
  cookies and has no server session.
- The Firebase web configuration in `js/firebase-config.js` and the VAPID
  public key. These are public by design — Google publishes them in every
  Firebase web app, and access is controlled by the security rules, not
  by hiding them. Please do not report them as leaked secrets.
- Anything requiring a rooted device, a compromised browser, or physical
  access to an unlocked phone.

## What is already assumed

Anyone on a trip can read and edit that trip. That is the product, not a
flaw. The interesting question is always whether someone can reach a trip
they are *not* on, or stay on one after being removed.

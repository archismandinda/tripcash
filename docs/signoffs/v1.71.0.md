## The four blockers, and what closed them

1. **`scripts/preflight.mjs` did not parse.** It was edited at 22:07 while
   the review was reading the tree, by the orchestrator, and left with an
   unclosed block. Fixed. This is RULEBOOK J6 — *never edit the tree a review
   is reading* — broken the same day it was written, by the actor it binds.
   The reviewer correctly caveated its entire verdict as covering a tree that
   changed underneath it.
2. **`pushProfileToTrips` wrote to a locked trip.** `syncNow` skipped locked
   trips *before* adding them to the set it then passed as the skip list, so
   editing your display name while locked out restamped your stale copy and
   won the merge when the lock lifted — erasing a co-member's rename or
   archive. ADR-0014's exact failure from the one path that set exists to
   close. Fixed by asking `writeAccess()` inside the function that performs
   the write, rather than at the two `continue`s the reviewer identified:
   there is a second caller that passes no skip set at all, and the rule
   belongs with the write. `tests/callsites.test.mjs` now names it, and was
   watched failing first.
3. **Version bump and changelog** — the story briefs forbid developers from
   doing this, so it is the orchestrator's, at the cut.
4. **A flaky test, found after the sign-off.** *"a member's grave outranks a
   row stamped ahead of this device's clock"* read `Date.now()` once to build
   the row and again in the assertion, so one millisecond passing raised the
   bar above the stamp the grave was computed from. It failed about one run
   in three. A flaky test in the one feature whose whole subject is stamp
   ordering teaches you to re-run instead of look. Clock pinned; six
   consecutive clean runs.

## Open decision

**How long member graves live.** Currently 90 days, like every other
tombstone. Remove somebody, then let a co-member's tablet stay closed for
three months, and that person returns with full access and nothing says so.
Keeping graves for the life of the trip is the cheap option and ADR-0024's
own reasoning supports it. Not decided; recorded in the ADR either way.

## What a user could still hit

- During the rollout window, someone removed may briefly regain access for
  one sync before it corrects itself.
- Settle-up rows on a locked trip are 75px tall instead of 46px at 375px.
- An empty read-only ledger still says "Log what you spend" beneath a notice
  saying changes are not accepted; the read-only expense sheet still says
  "locked in when you save" on a sheet that can never be saved.

## What was NOT verified

- **Anything against real Firestore with real accounts.** The
  `permission-denied` → lockout → lock-lifts-on-next-read loop was never run
  end to end; it was driven by setting the marker directly and reading
  `syncNow`. The pure decision is proven and adversarially probed; the app
  wiring around it is source-read only.
- **`pushProfileToTrips` live.** The gap was proven by reading a three-line
  control flow, not by watching a timestamp move. The fix is likewise covered
  by a source-grep test, not an observed write.
- **Two genuinely separate physical devices.** All merge findings come from
  the real modules in a faithful build → merge → apply loop.
- **iOS Safari.** Everything visual was measured in Chromium. The read-only
  checkbox paint deliberately avoids `::after` for iOS reasons that remain
  untested on an actual iPhone.
- **Push notifications, the receipt viewer on a locked trip, and dark mode**
  for the new read-only surfaces.
- **Restore from backup.** No backup exists (TD-10). Still the highest
  severity item on any backlog here.

# v1.72.0 — release record

**One change, decided by the owner: member graves are kept for the life of
the trip.** Cache `tripcash-v98`. 10 Aug 2026.

> **This did not go through a sprint's independent QA lane, and that is a
> real difference from every other version here.** It was implemented and
> verified by the orchestrator alone, immediately after v1.71.0's sign-off
> left the decision open and asked for it to be recorded either way. Stated
> plainly rather than left for someone to infer from the absence of a
> reviewer's name.

## The change

`mergeRoster` no longer prunes member graves. Everything else — expenses,
settlements, attribution — keeps ADR-0008's 90-day TTL, unchanged.

The TTL was inherited, not chosen. Past the line a grave was pruned, and a
co-member's phone still carrying the removed row brought that person back —
row, uid, read and write access, notifications — telling nobody.

The argument for pruning was Firestore's 1 MB document ceiling, and it does
not survive measurement: 200 removals over a trip's entire life cost 5,401
bytes, 0.52% of the limit. Real trips remove one or two people. An expense
grave is one of hundreds; the two cases only looked alike.

## Verified

| | |
|---|---|
| `npm test` | 815 pass, 0 fail — run three times |
| `npm run test:rules` | 57 pass, 0 fail |
| `npm run preflight` | clean, all 8 checks |

- The inverted test keeps the old assertion quoted in place, because it
  encoded a defect rather than a decision.
- A control test proves **expense** graves still prune at 90 days — the
  decision was that members are unlike expenses, so it must not have leaked.
- **The re-add case**, driven through the real `planAddMember` and
  `mergeRoster`: remove Bala, wait 100 days, add him back against a
  co-member's stale roster. He returns with a fresh UUID, the old grave for
  `m-b` is still present, and the merge keeps both. This was the one case a
  permanent grave could plausibly break.

**What the drill did not prove:** the restored *contents*. There is no
`gcloud` on this machine and no Admin SDK credentials, so the clone could
not be read. "A restore completes and yields a working database" is
verified; "the data came back correct" is not. That needs a canary document
written before the snapshot and read back from the clone, and it needs a
read path this machine does not have.

## What was NOT verified

- **No independent QA.** No second agent reviewed this; the tests are the
  only check, and they were written by the same author as the change.
- **Nothing against real Firestore**, and nothing on hardware.
- **The very long tail**: a trip that removes people for years. Measured by
  arithmetic, not observed.
- Restore from backup — still no backup (TD-10).
